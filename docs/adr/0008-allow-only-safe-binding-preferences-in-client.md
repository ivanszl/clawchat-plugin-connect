# Allow only safe Binding preferences in Connect Client

The ordinary Connect Client Binding-preference mutation may update only `displayName`, `model`, `modelReasoningEffort`, and the default `outputVisibility`. Executable and environment overrides, Binding-level additional directories, ClawChat activation, and arbitrary Binding config keys remain outside that mutation. Connect Service validates this boundary server-side.

The Plugin administration surface separately allows the loopback Client (or its private loopback Liveware gateway) to create an Agent Binding from an installed, active Runtime capability and to edit the exact `pluginId`, `capabilityId`, and capability-owned `runtimeConfig` of a Binding whose Binding Runtime is not active. This is not an expansion of the preference mutation: Connect validates the exact provider against the active Plugin Registry and validates `runtimeConfig` against the capability's JSON Schema before atomically persisting the Binding. An active Binding must be stopped before its provider or provider configuration can change.

Project registry and Session controls are separate semantic interfaces, not arbitrary Binding preference updates. Connect Client may register a Project root, remove an unreferenced Project, and select one of the Runtime Adapter's advertised modes for a Session. These operations are validated against the Project Catalog and the Adapter's finite mode catalog. They are available through the same unauthenticated local Interface and therefore inherit ADR-0016's loopback-by-default and trusted-LAN security boundary. ADR-0041 removes the former Project additional-directory capability.

All allowed preferences take effect immediately. If a turn is active, saving succeeds without cancelling it and the new preference applies to the next turn. For runtime turn options such as model and reasoning effort, Connect preserves the Runtime Thread ID, releases the in-memory Runtime Adapter session after the active turn, and resumes that same Thread with the new options rather than invalidating conversation context.

Session and Session Intent may carry a more specific model and reasoning-effort selection. The effective model resolves Session selection, then this Agent Binding default, then the Runtime Adapter's advertised default. Reasoning effort resolves independently: a persisted Session effort is strict, a valid Binding default is used for the effective model, and otherwise the model's advertised default is used. Connect validates catalog-backed selections before persistence and never silently replaces an unavailable persisted Session model or effort. A Binding effort is a fallback preference; if catalog changes make it invalid for the effective model, the advertised model default applies.
