# Mount a Connect-owned DeepSeek Harness bridge

The official DeepSeek Harness Runtime Plugin carries an exactly paired DSH Integration Bridge and composes it only for the lifetime of its Binding Runtime Instance, without adding a dependency or Bridge entry to the user's selected DSH Profile manifest or user patch. Here “mount” is configuration composition, not a filesystem mount or plugin installation: Connect generates an external Cordis patch file and passes it as the final `dsh --patch <path>` layer when starting its owned process. DSH documents `--patch` as a supported CLI composition mechanism. The generated layer disappears when omitted on the next launch, and Connect never runs `dsh plugin add` for the Bridge.

The Bridge itself and the Bridge-to-Adapter protocol are Connect-defined; DSH does not ship an official Connect Bridge or a public Runtime Adapter protocol. The Bridge runs inside DSH because the current public SDK does not expose all native Session, cancellation, interaction, catalog, and lifecycle surfaces required by Connect. Where the Bridge injects an internal DSH service rather than calls a documented public API, the DSH capability profile must label that route as internal and version-pinned. Keeping it Connect-owned avoids a second user installation and keeps both sides version-compatible, while the user's DSH Home, Profile, credentials, and plugin composition remain DSH-owned. DSH may still maintain its own generated Profile bootstrap files during an ordinary launch; Connect treats those as DSH-owned behavior rather than claiming that the Profile directory is byte-for-byte immutable.

The Bridge is an adapter, not a capability-completion bundle. Its process-only patch may add the Bridge row and the minimum configuration required for its own transport, but it must not add DSH Web, storage/workspace, or other feature services merely to make a capability appear available. Capability detection reflects the selected Profile's native composition; a missing native service produces `unsupported` rather than a Connect-assembled substitute.

The transport is two inherited anonymous pipes and a Connect-owned version/capability handshake; it does not use DSH stdin/stdout or open a listener. The Runtime Plugin carries the Bridge's exact dependency closure because an out-of-tree module cannot assume DSH's package dependencies resolve from its own path. It may bundle value-only helpers or ship pinned private dependencies, but it must consume service instances from the selected DSH composition rather than bundle duplicate DSH service runtimes.

The [throwaway published-runtime prototype](../../.scratch/deepseek-harness-integration/prototype/result.md) proved this composition boundary against DSH `0.1.0-rc.7`: an absolute Bridge artifact outside the Profile composed through a final `--patch` overlay, received the selected Home and Workspace, disposed on `SIGTERM`, disappeared when the overlay was omitted, and left the Profile manifest and user patch unchanged. The prototype proves technical feasibility, not that DSH guarantees the Connect-owned Bridge or its use of internal services as a stable public API. Its separate experiment that added DSH Web storage/workspace services to a base-only Profile is explicitly rejected as a production fallback.
