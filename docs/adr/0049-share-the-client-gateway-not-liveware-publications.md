# Share the Client Gateway, not Liveware publications

Core owns one Shared Client Gateway for the installation and gives the official Liveware Exposure only its opaque loopback upstream address. Other Client Exposure Plugins use the narrower Core-mediated Client fetch facade. The official Liveware Plugin acquires and releases the Gateway endpoint and owns one installation-scoped Liveware Exposure, while each activated Agent Binding owns an independent Binding Liveware Publication: one private managed Liveware App, URL, tunnel to the Gateway, and ClawChat Liveware Registration administered with that Binding's credential. Core starts the Gateway for the first Liveware lease and stops it after the final lease releases it. Removing a Binding retires only its publication; retirement unregisters its launcher and deletes its App, whose deletion authoritatively retires the tunnel without requiring a separate unbind operation. Disabling or removing the Liveware Plugin commits only after every publication is retired and its Gateway endpoint is released; a failure leaves the Plugin enabled with its credentials and cleanup progress for explicit retry rather than creating an orphan or hidden cleanup-only instance. Owner Reset retains its existing product semantics outside this decision. A publication failure is isolated from its Agent Binding, Runtime, ordinary messages, local Client access, Shared Client Gateway, and other publications. Publication lifecycle is persisted and reconciled from its exact remote identity; confirmed idempotent gaps may converge automatically, while indeterminate effects block duplicate creation or destructive follow-up. A failed Binding removal reports failure, preserves the Binding, credential, and cleanup progress, and requires another explicit removal request rather than deleting later in the background. This supersedes ADR-0046's single-App and single-tunnel topology, while retaining its one Installation Owner, installation-wide Connect Client, shared Gateway, private access, and failure-atomic cleanup decisions.

ADR-0051 confirms that any normally validated installed Plugin may contribute Client Exposure; the Gateway-sharing and per-Binding Liveware publication topology remains unchanged.

The rejected Liveware topology used one App and tunnel for all Bindings plus a designated controller credential. Real APIs accepted duplicate launcher registrations, but launcher and authentication support for sharing one App was not established, and the Control Plane rejected App administration by a different same-owner Agent. Independent publications align authority, lifecycle, and cleanup without credential rotation. Plugin-owned or per-Binding gateways are also rejected: Host, Origin, and spoofed-scope-header enforcement protect a Core interface and must not vary by Exposure Plugin, while every publication exposes the same installation-wide Client.
