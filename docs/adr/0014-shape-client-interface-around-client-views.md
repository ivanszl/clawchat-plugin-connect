# Shape the Client Interface around Connect Client views

Connect Service will expose a Client Interface tailored to the Connect Client rather than a generic wrapper over Runtime Adapters or SQLite tables. Queries return presentation-ready Connect-owned views—including the Project and Non-Project Session tree, Session header and status, ordered Transcript blocks, pending Runtime Interactions, capability-driven actions, completeness, and pagination—so the Client does not reproduce backend joins or runtime state machines. Commands express semantic user intent and return the resulting resource state or revision.

The Interface is UI-shaped but not UI-library-shaped. It uses stable IDs, explicit states, timestamps, ordering, origin, summaries, structured details, available actions, and plain-text fallbacks; it never returns React elements, HTML generated by a runtime, Astryx props, CSS classes, app-server methods, or ACP payloads. Rich Runtime Adapter events are mapped into a versioned Connect block union for messages, reasoning summaries, plans, tools, commands and terminal output, file changes and diffs, progress, usage, errors, and Runtime Interactions. Unknown native events remain preserved in the projection and appear as a safe generic block instead of being silently discarded.

Session Catalog entries expose a presentation-only Workspace Group backed by a synchronized Project for every active persistent Runtime Workspace Identity with a usable local root. Connect reuses a Project with the same canonical root or creates the missing Project during synchronization; it does not delete Projects merely because their Runtime Threads later become inactive or archived. Runtime Adapters classify runtime-specific generated scratch workspaces as transient, and the Catalog keeps those Runtime Threads as direct Non-Project leaves rather than exposing meaningless directory names.

ClawChat's `/project` control consumes the same binding-scoped synchronized Project choices and root-derived labels as Connect Client. Archived-only and Runtime Adapter-classified transient workspaces are not synchronized or selectable; registered Projects remain selectable even when they have no active Runtime Thread. The interaction surfaces therefore agree on one Project collection rather than exposing an intermediate unsynchronized Runtime Workspace choice. Project selection uses the root-derived Workspace ID on every user-facing surface; names and paths are display-only, the persisted Project ID remains internal, and `/project none` is the sole non-ID control.

This synchronization is intentionally one-way. Codex app-server exposes Runtime Thread discovery and lifecycle plus `cwd`-based thread start and configuration, but no Project collection or Project create/delete lifecycle. Connect therefore projects active persistent Runtime Workspace Identities into its own Projects and uses a Project root as the runtime `cwd`; it does not claim that changing a Connect Project mutates a corresponding runtime-owned Project object.

Initial browser transport uses HTTP for snapshots and semantic commands and SSE for ordered server-to-Client view changes. Each event carries a monotonically increasing cursor and stable entity revision so TanStack Query state can merge updates idempotently; reconnect uses `Last-Event-ID`, and a cursor gap instructs the Client to reload the affected snapshot. A future transport change must preserve this Client Interface rather than changing view semantics to match the transport.
